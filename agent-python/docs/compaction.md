# Compaction behavior

This document describes the compaction currently implemented in `agent-python` and compares it with the three production-oriented guidelines: phased compaction, structured meta-compaction, and decoupled reflection.

## Executive summary

The implementation has a phased, asymmetric compaction design with hybrid reflection enabled by default. It preserves the system prompt and original goal separately, sends a reflected lesson ledger as a system message, and keeps the newest configured messages raw. Optional workflow graphs keep phase evidence and transition history outside compactable raw memory, so compaction cannot erase proof that a phase completed.

The hybrid path combines structured reflection with the raw sliding buffer. The compaction prompt requires XML-style sections for the goal, global lesson ledger, dead ends, and current local pivot. The result is still unvalidated text, but reflection is now explicitly asked to turn verified discoveries into imperative operational rules. Reflection can be disabled with `memory.hybrid_reflection: false`; the default is `true`.

## What is implemented

### 1. Asymmetric phased compaction: implemented

`AgentEngine._compact_if_needed()` divides memory into:

```text
[system prompt]
[immutable original goal]
[compacted context ledger]
[raw retained messages]
```

The original goal is stored in `SessionState.goal` and is also retained as the first memory message. When compaction runs, the engine uses:

```python
historical = state.memory[1:-keep]
raw = state.memory[-keep:]
```

The initial goal message is excluded from the historical prefix, and the latest `keep` messages remain untouched. The engine then replaces mutable memory with the goal plus the raw tail:

```python
state.memory = [state.memory[0], *raw]
```

This means the implementation does not flatten the entire conversation. Recent assistant actions, tool calls, tool results, user messages, and error messages in the retained tail remain available at full fidelity.

`SessionState.workflow` is deliberately not part of this mutable raw list. When a tool invocation matches a configured phase-evidence rule, the engine records a durable evidence key and any resulting phase transition before the next compaction can run. A phase may also declare `allowed_tools`; calls to later-phase tools are recorded as workflow errors and are not executed. This lets a Case 3 failure/retry sequence compact safely while retaining its completed phases and current phase.

The default setting is:

```yaml
memory:
  max_tokens: 6000
  max_steps: 12
  raw_turns_to_keep: 3
```

Important precision: `raw_turns_to_keep` counts messages, not semantic user/assistant/tool turn groups. A tool interaction can consume multiple messages, so the retained buffer is not guaranteed to contain exactly three conversational turns.

Compaction is triggered when the approximate in-memory token count reaches `max_tokens`, or when `step_count` reaches `max_steps`, provided there is more memory than the goal plus the raw buffer. Token usage is estimated as `len(content) // 4 + 1` per message.

### 2. Hybrid reflection and structured meta-compaction: implemented with validation gaps

When `memory.hybrid_reflection` is enabled, `LlmClient.compact()` instructs the model to emit exactly this structure:

```text
<COMPACTED_STATE>
<USER_GOAL>...</USER_GOAL>
<GLOBAL_LESSON_LEDGER>...</GLOBAL_LESSON_LEDGER>
<DEAD_ENDS>...</DEAD_ENDS>
<CURRENT_LOCAL_PIVOT>...</CURRENT_LOCAL_PIVOT>
</COMPACTED_STATE>
```

The reflector is told to analyze only the historical prefix, preserve verified facts, express durable discoveries as imperative rules, and keep dead ends precise. The existing ledger is supplied on later compaction calls, so the model can carry forward earlier lessons while incorporating newly historical messages.

The ledger is inserted into the next decision payload as a system message prefixed with:

```text
[COMPACTED CONTEXT STATE]
```

The raw working buffer is not generated by the reflector. The engine places a `[RAW WORKING BUFFER — PRESERVE VERBATIM]` delimiter before the retained messages in the next decision payload. This is safer than asking a summarizer to copy raw errors, because the actual messages remain untouched in `SessionState.memory`.

The implementation does not yet enforce the reflected format after generation. The model can return arbitrary text, tags can be missing or duplicated, and the fields are not represented as a typed object with explicit weighting metadata.

When the compaction endpoint fails, the hybrid fallback emits the same XML-style sections, records that no verified lessons or dead ends were extracted, and directs the agent to inspect the retained raw buffer. It does not invent a lesson from unavailable model output.

When `memory.hybrid_reflection: false`, the existing four-heading compaction path is used. Phased compaction and raw-buffer retention still operate; only the reflection-oriented prompt and XML-style ledger are disabled.

### 3. Pure decoupled reflection: intentionally not implemented

There is no separate phase that drops the historical ledger and appends only one high-priority operational rule beneath the system prompt. The hybrid implementation intentionally keeps both the reflected ledger and the raw working buffer. It does not:

- ask for a single most important lesson;
- produce a durable operational rule separate from the ledger;
- append a standalone rule immediately below the system prompt;
- maintain a distinct collection of self-correction rules; or
- prioritize a new rule over the rest of the compacted context.

The `CURRENT_LOCAL_PIVOT` section is the closest behavior, but it remains part of the general compaction output and is not treated as an independently enforced instruction.

## End-to-end flow

For each active run step, the engine follows this order:

1. Evaluate one configured workflow transition from durable tool evidence, if workflows are enabled.
2. Estimate tokens and check compaction thresholds.
3. If due, send the historical prefix plus the prior ledger to `LlmClient.compact()`.
4. Replace the historical prefix with the returned reflected ledger and retain the raw tail.
5. Build the decision payload from the system prompt, immutable goal, active workflow phase, ledger, a raw-buffer delimiter, and raw memory.
6. Ask the model for either a tool call or a final answer.
7. Append the assistant action and tool result to mutable memory, recording matching workflow evidence outside that memory.
8. Accept a final answer only after the workflow terminal node is reached; otherwise retain prose progress and continue until the bounded step limit.

Tool failures are appended as tool-message content, so they can be included in either the raw buffer or a later ledger. This supports the goal of preserving recent failures, although the fallback ledger does not reliably categorize them as dead ends.

## Gaps and risks

### Threshold and token accounting

- The token estimate counts message content but not tool-call JSON arguments, message metadata, or the serialized system/ledger payload. Actual request size can therefore be larger than the estimate.
- `max_steps` is also the default run limit. In the normal default run, the loop stops when it reaches that limit, so a compaction check based on `step_count >= max_steps` generally cannot run after the final step. It is useful when a caller runs with a larger explicit step limit, but it is not a reliable independent compaction trigger in every execution mode.

### Turn boundaries

- The retained unit is a message count, not a turn-aware group. A production implementation may want to retain complete user/assistant/tool interaction groups so a tool call is not separated from its result.

### Ledger integrity

- The LLM output is not parsed or validated against the four required fields.
- There is no explicit maximum ledger size.
- The fallback labels arbitrary trailing history as `Dead Ends`, which can misrepresent successful discoveries.
- The ledger has no machine-readable confidence, provenance, timestamp, or distinction between verified and provisional claims.

### Reflection and weighting

- Hybrid reflection is configurable through `memory.hybrid_reflection` and defaults to enabled.
- The system prompt, immutable goal, reflected ledger, and raw buffer are ordered by role, but there is no explicit weighting mechanism beyond placement and the compaction prompt.
- The current pivot is not guaranteed to be the single highest-priority instruction at decision time.

### Workflow/evidence integrity

- Workflow evidence is currently matched against configured tool name, argument subsets, JSON-result subsets, and optional output substrings. It is intentionally declarative but not cryptographically signed.
- A workflow graph may contain future branch/skip edges (`evidence` and `always`), so configuration authors must avoid accidental cycles; the run-level step limit is the finite safety boundary.
- Session state and its resolved immutable config snapshot are persisted as JSONB in PostgreSQL. The API reloads them after a restart; streamed lifecycle events are retained in an append-only PostgreSQL event table. Multiple API replicas would still need a distributed lock around concurrent resumes.

## Compliance matrix

| Guideline | Status | Evidence in implementation |
| --- | --- | --- |
| Keep system prompt and original goal intact | Implemented | `SessionState.goal` and `_payload()` |
| Compact only the historical prefix | Implemented | `state.memory[1:-keep]` |
| Keep recent raw context | Implemented, message-based | `raw_turns_to_keep: 3` |
| Use a structured lesson ledger | Partial | Hybrid XML-style sections are required, but output is not validated |
| Preserve verified truths and dead ends separately | Partial | Reflection prompt and fallback separate them; no post-generation validation |
| Maintain a highest-priority local pivot | Partial | `CURRENT_LOCAL_PIVOT` is explicit but not independently enforced |
| Add hybrid reflection | Implemented, configurable | `memory.hybrid_reflection`, default `true` |
| Preserve phase evidence across compaction | Implemented, configurable | `SessionState.workflow` and evidence-gated graph transitions |
| Prevent premature final completion in workflow mode | Implemented | Terminal workflow node required before `status="complete"` |
| Add a pure decoupled reflection rule | Intentionally missing | Hybrid design retains ledger plus raw buffer |

## Bottom line

The current implementation satisfies the sliding-splice idea, configurable hybrid reflection, and durable workflow evidence. The most important missing production safeguards are turn-aware retention, strict ledger parsing/validation, accurate token accounting, durable session persistence, and independently enforced self-correction rules.
